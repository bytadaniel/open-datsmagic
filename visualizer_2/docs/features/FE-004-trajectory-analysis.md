# FE-004: Расчет и отбор прогнозных траекторий

## 1. Контекст

Показывать оператору информативное подмножество веера, а не сотни линий: текущий курс, выгодные по фактической bounty отдаче варианты и аварийный вариант, если безопасной прибыльной альтернативы нет.

## 2. Одна симуляция на направление

- Сканировать полный круг с пользовательским угловым шагом `1°..20°`; по умолчанию `1°`. Каждый кандидат рассчитывается один раз на snapshot revision, результаты переиспользуются для сортировки и paint.
- Горизонт рисования визуализатора — `75 с`, чтобы маршрут мог охватить почти всю арену. Сравнительное окно `agile-top1` — `15 с` после lead задержки команды `0.3 с`, то есть первые `15.3 с` от снимка; этот участок интегрируется шагом `0.2 с`, как у игрока. После него дальний хвост прореживается логарифмически до `0.8 с`. Текущий прогноз удерживает последний applied `selfAcceleration`; веер сначала удерживает известную команду в задержку, затем применяет кандидатный maxAccel в фиксированном направлении.
- Интегрировать velocity/friction/anomaly forces по root `docs/mechanics.md` и `players/player_2/src/planner.rs`. Сдвигать аномалии линейно по velocity.
- Bounty засчитывается один раз, когда сегмент пересекает круг радиуса `transportRadius + bounty.radius`, синхронный серверному capture radius (в текущем API оба радиуса равны радиусу ковра); событие после смертельной точки не засчитывается. Используются реальные `points`, near-miss potential не добавляется.
- Для маршрута `routeScore = sum(points)` и `timeToLastBounty = время события последней bounty`; `scoreRate = routeScore / max(0.2, timeToLastBounty)`, как `score_rate()` в player_2. Показывать оба значения и rate в HUD.
- Ранг золотого маршрута рассчитывать по точным первым `15.3 с` от снимка: безопасные кандидаты с реальными bounty сортируются по `scoreRate = scoreДо15.3с / времяДоПоследнейМонетыДо15.3с`, затем по score и скорости, как `player_2 agile-top1` (15 секунд candidate horizon + 0.3 секунды lead). При свежей telemetry для `agile-top1` также исключить монеты, уже зарезервированные коврами с ID, сортировочно предшествующими выбранному. Порог видимого score-rate не должен менять top-1 или удалять его из отображения. Если прибыльных путей нет, top-1 выбирается среди безопасных пустых направлений; если безопасных нет — среди смертельных с максимально поздним прогнозом смерти. Рисуемый хвост при этом продолжается до 75 с. Текущая фактическая траектория показывается отдельно.
- Первое смертельное событие: ядро аномалии, столкновение транспорта, либо пересечение границы. Проверки столкновений и bounty остаются swept по всему сегменту каждого переменного шага, чтобы не пропускать быстрые пересечения. Прогноз обрывается в точке события; каждый отображаемый маршрут, включая текущий и каждый элемент веера, рисует там компактный крест. Дальний участок — приближение траектории крупным шагом; точность столкновений с искривлёнными траекториями ниже, чем на ближнем участке.
- В каждой прогнозной траектории хранить elapsed time для каждой точки. Кандидатные траектории, кроме текущей и топ-1, рисовать отдельными сегментами с цветом по времени прохождения: зелёный у начала прогноза, переход к жёлтому в середине, затем к пурпурно-красному у конца горизонта. Цвет зависит только от elapsed time / horizon, никогда от евклидовой близости. Текущая и топ-1 сохраняют свои статусные цвета; крест смерти всегда красный.

## 3. Интерактивные параметры и категории маршрутов

- Настройка прогноза в HUD минимальна: один слайдер угловой дискретности 1°–20° (по умолчанию 1°), который напрямую управляет основным объёмом расчёта. Первые 15.3 с от снимка используют шаг 0,2 с и формируют Agile top-1; дальний хвост до 75 с нужен для пространственного контекста и имеет шаг до 0,8 с. Фильтры видимости не влияют на вычисление и показ золотого top-1. Число маршрутов переключается кнопкой минимальный набор / весь веер.
- Изменение углового шага инвалидирует кэш направлений и немедленно пересчитывает веер в том же кадре. Переключатель `P` меняет только видимость (current + top-1 либо все ранжированные маршруты), не зависит от их количества и не сбрасывается при обновлении списка.
- Золотой маршрут является именно Agile top-1 бенчмарком. Его совпадение с фактическим выбором игрока гарантируется только при `DATS_PLAYER_STRATEGY=agile-top1`, шаге игрока 1° и актуальной telemetry; `stable-profit` намеренно может удерживать иной курс даже при movement target `aim`.
- Применить min/max score-rate можно независимо: безопасные прибыльные маршруты показываются только внутри диапазона. Если он пуст, веер прибыльных маршрутов пуст, но текущий курс и смертельные fallback-маршруты остаются доступны.
- Все отобранные прибыльные маршруты (или смертельные fallback-маршруты, если прибыльных нет) сохраняются в порядке score-rate / времени выживания. Текущий маршрут и кандидат ранга #1 всегда отображаются независимо от режима и фильтров категорий. Кнопка или `P` переключает минимальный набор (текущий + топ-1) и полный список.
- Категории траекторий дополнительно фильтруются отдельными переключателями: текущая, прибыльные кандидаты, смертельные fallback. Текущий путь и топ-1 кандидат всегда видны. Текущий путь сохраняет цвет статуса (золотой, если сам является top-1, синий обычный, красный смерть); кандидат #1 всегда золотой. Остальные маршруты окрашиваются временным градиентом согласно elapsed time каждой точки; смертельная точка всегда отмечается красным крестом.
- Текущая траектория получает порядковый rank в списке безопасных прибыльных маршрутов, отсортированном тем же 15.3-секундным окном; верхний порог score-rate не применяется. HUD отдельно показывает метрики окна Agile и всего 75-секундного прогноза. При rank 1 текущая линия золотая; смертельная линия всегда красная.
- Изменение угловой дискретности пересчитывает прогноз; переключение видимости полного веера меняет только paint. Кэш учитывает все влияющие на расчёт поля. UI показывает число направлений, фиксированный горизонт и правило переменного временного шага.
- HUD объясняет единственный расчётный регулятор: `Scan step` — угол между кандидатами (больше = меньше расчёт и грубее выбор). Дальний горизонт и адаптивный шаг предназначены для пространственного обзора, а не для строгого ранжирования 1:1 с серверным `agile-top1` (его горизонт 15 с и постоянный шаг 0,2 с).
- Top-1 не ограничен фиксированным диапазоном score-rate: он совпадает с ранжированием `agile-top1`, даже когда score-rate выше 100/s. Категории `Current`, `Score routes`, `Death routes` остаются простыми переключателями и не скрывают обязательные текущий маршрут и топ-1.
- Золотой маршрут — точный `agile-top1` benchmark при угловом шаге 1° и свежей telemetry; при большем шаге это лучший из показываемых направлений. `stable-profit` намеренно может держать другую прибыльную траекторию. При `movement_decision=aim` расхождение не является survival-переопределением, а для `stable-profit` само по себе не является багом.

## 4. Производительность

- Пересчитывать кандидатов только при изменении snapshot, выбранного транспорта, bounty/anomaly state или параметров веера; cache key включает все влияющие поля.
- Раздельно измерять время forecast и render. Не делать аллокации на каждой симуляционной точке сверх одного набора точек в candidate cache.
- Painter получает точки пакетами; на кадре рисуются только выбранное число ранжированных маршрутов плюс текущий курс, если он входит в выбранный префикс.

## 5. Проверки

- [ ] Unit: сегментные bounty/collision пересечения дают правильное время события и score.
- [ ] Unit: `scoreRate = score / max(0.2, lastTime)`, near miss = 0 points.
- [ ] Unit: safe profitable candidates сортируются по убыванию rate, empty routes исключаются, fallback дает максимальное `deathAt`.
- [ ] Unit: death location равна последнему интегрированному событию; маленький крест рисуется у любого показанного смертельного кандидата.
- [ ] Benchmark: повторный кадр того же cache key не пересчитывает прогноз; целевая типовая сцена — 60 FPS.
