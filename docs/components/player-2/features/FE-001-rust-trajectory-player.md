# FE-001: Отдельный Rust-игрок с прогнозированием траекторий

## 1. Контекст и бизнес-цель

Создать второй клиент-игрок, который самостоятельно анализирует мир, предсказывает движение флота и отправляет команды. Он не должен добавлять код стратегии или зависимости в серверный executable. Исходный TypeScript `datsmagic` сохраняется как player_1.

## 2. Архитектурное решение

- `lib/arena-bots/player_1/` — архивная копия прежнего клиента, если восстановлена в рабочем checkout.
- `lib/arena-bots/rust_bytadaniel/` — самостоятельный Cargo package и Git submodule, отдельный от workspace сервера; только минимальные зависимости JSON и отдельный исполняемый файл.
- Token resolution: non-empty `DATS_PLAYER_TOKEN` is used directly; otherwise read the path in `DATS_PLAYER_TOKEN_FILE`, defaulting to `token.txt`. This prevents a shell-provided token from silently targeting a different fleet.
- Стратегию задаёт `DATS_PLAYER_STRATEGY`: `stable-profit` (основная, по умолчанию), `agile-top1` либо `top1-v2`. Неизвестное имя стратегии считается ошибкой конфигурации.
- Movement задаётся независимо через `DATS_MOVEMENT_STRATEGY=none|survival`; при `survival` каждый тик оценивается риск текущего aim-курса и при угрозе выполняется safety scan. Escape включается, если до прогнозируемой гибели осталось не более 3 секунд или безопасных вариантов осталось не более 10% скана. Если выход не найден в горизонте, `DATS_DOOM_POLICY=collect|fastest` выбирает максимизацию bounty до смерти или кратчайшую смерть. Переменные по умолчанию: `none` и `collect`.
- Единственный API — `POST /play/magcarp/player/move`. Пустой пакет опрашивает мир, обычный пакет одновременно опрашивает и отправляет команды пяти коврам.
- `DATS_SERVER_URL` принимает HTTP- или HTTPS-origin без пути. Для HTTPS клиент устанавливает TLS с проверкой имени хоста и сертификатной цепочки по встроенным публичным WebPKI trust roots; отключённой проверки сертификата и самоподписанных сертификатов по умолчанию нет.
- Решатель моделирует игровое обновление Эйлера: `V' = clamp((V * friction) + (A + W) * dt, maxSpeed)`, `P' = P + V' * dt`; будущая аномалия смещается линейно по `velocity` перед каждым шагом.
- Для каждого ковра coarse scan равномерно покрывает все 360° с шагом 5° — 72 направления; до трёх лучших локальных областей уточняются с шагом 0,25° в окнах ±3°. Задние направления, включая полный разворот, входят в coarse scan наравне с остальными. Если все направления смертельны, выбирается предпочтительная смертельная траектория; повторный аварийный круг не требуется.
- Цели траектории: `CollectBounties`, `AvoidDeath`, `FastestDeath`. Каждый живой ковер независимо строит и оценивает свои направления; fleet reservation исключает повторное закрепление одной bounty за несколькими коврами.
- Каждая траектория останавливается на первом касании ядра, границы карты или транспорта. Монета считается собранной при касании суммы радиусов на сегменте движения за серверный тик.
- RTT ответа сглаживается EWMA; перед применением кандидатной команды состояние упреждается на RTT + оценку фазы тика.
- Отправка ограничена одним запросом с командами на тик; `429` вызывает ожидание тика с jitter/backoff, не меняя команду.
- После каждого успешного планирования player_2 атомарно обновляет локальный JSON telemetry snapshot для совместного чтения визуализатором. По умолчанию путь в системном temp-каталоге с token hash; `DATS_PLAYER_TELEMETRY_FILE` позволяет задать общий путь явно. Snapshot содержит стратегии, tick/budget и per-carpet логи выбранного решения; токен и bounty snapshot туда не записываются. Консоль оставляет компактный общий статус, подробности конкретного ковра показываются в панели визуализатора.

## 3. Схема базы данных

Не применяется: план хранится в оперативной памяти процесса, восстановление состояния идет из Desert API.

## 4. Алгоритмы и вспомогательные функции

### Прогноз

- Основной подшаг равен серверному `tickRate` 0,2 с; в `stable-profit` прогнозный горизонт после применения команды — 30 с по умолчанию, в `agile-top1` и `top1-v2` — 15 с. Переменная `DATS_PLAN_HORIZON_SECONDS` задаёт горизонт основной стратегии; для обеих top1-стратегий действует жёсткий предел 15 с. От текущего снимка моделирование дополнительно включает lead задержки команды (0,3–0,8 с).
- Ускорение кандидата постоянно по длине `maxAccel`, направление дискретно перебирается.
- Сила аномалии пересчитывается по будущему положению транспорта и будущему положению аномалии; положительный `strength` направлен к центру, отрицательный — от него.
- `coreRadius + transportRadius` задаёт lethal-radius. Сбор bounty моделирует серверную swept-проверку: на каждом шаге `0.2 с` минимальное расстояние от центра bounty до отрезка движения ковра сравнивается с суммой `transportRadius + bounty.radius` (сейчас 10). Засчитывается даже частичное пересечение кругов между endpoint-ами; bounty после прогнозируемой смерти не собираются. Для большого пула применяется ограниченный shortlist ближайших и наиболее ценных целей.
- При оценке курса учитываются фактические пересечения и запас до края радиуса захвата, собранные points, число bounty, время до награды, время выживания, риск, цена смены угла и удержание действующей цели.
- Среди безопасных курсов с наградой выбирается курс с максимальной суммой ожидаемых points (с поправкой на время получения); число пересечённых монет — дополнительный критерий, поэтому несколько дешёвых монет не обязаны перевешивать одну дорогую.
- Метрики выбора цели: `totalPotentialScore` равен сумме фактических сборов до столкновения, каждый сбор дисконтирован как `points * exp(-eventTime / 15)`, плюс только один бонус лучшего несобранного bounty: `points * 0.3 * exp(-minDistance / 450) + points * 0.05 * nearMissRatio`, где `nearMissRatio = clamp(1 - max(minDistance - captureRadius, 0) / 18, 0, 1)`. Дистанция минимума считается по непрерывным отрезкам траектории. Поэтому это прогнозная utility, а не только гарантированные очки. При отсутствии bounty применяется штраф `-distance(endpoint, mapCenter) / 100`. `timeToReachScore` — время от снимка до первого серверно-валидного касания bounty или ближайшего сближения с учётом RTT lead.
- `PlanMemo.target` — первая фактически пересекаемая bounty на сохранённом безопасном маршруте. Пока цель существует и прежний фиксированный вектор всё ещё безопасно ведёт через неё в пределах горизонта планирования, бот проверяет этот курс одним точным 30-секундным прогнозом и пропускает полный веер. Когда сервер подтверждает сбор/исчезновение этой bounty, цель немедленно освобождается: в том же новом снимке бот заново оценивает веер и переключается на лучший безопасный маршрут. Если прежний путь стал смертельным или больше не пересекает цель, фиксация также снимается и безопасность/новый лучший курс имеют приоритет. Потенциальная near-miss цель не закрепляется как первая монета.
- Для закреплённой bounty запоминается её target-specific ETA. За следующий тик прогнозируемое ETA должно уменьшиться примерно на 0,2 с; допуск прогресса — 0,12 с. Два последовательных тика без прогресса означают, что фактическое состояние уходит с перехвата: фиксированное направление освобождается и запускается широкий scan. Потеря безопасности или пересечения цели освобождает курс сразу.
- Пока базовая цель удерживается, выполняется тактический scan всего круга шагом 10° на 5-секундном горизонте. Три лучшие локальные области, в том числе перспективные near-miss, уточняются шагом 0,25°; их первый собранный bounty и ETA формируют `firstBountyRate = target.points / targetETA`. Только близкая (ETA ≤ 5 с), безопасная на полном 30-секундном горизонте монета с rate выше базового на `max(50%, 5 points/s)` становится временным detour. Обычный длинный `scoreRate = routeScore / timeToLastBounty` остаётся отдельной метрикой. Для привязанной цели консоль отдельно выводит первый `points/ETA`.
- Перед detour сохраняются исходные угол и целевая bounty лишь как resume-кандидат. После подтверждённого сбора detour-монеты выполняется полный выбор по актуальному снимку: обычный круговой scan, локальное уточнение и сопоставление безопасных кандидатов. Прежний курс включён в кандидаты и прогнозируется заново, но не восстанавливается автоматически; выигрывает маршрут по текущим правилам безопасности, скорости и score-rate. Detour не вкладываются друг в друга.
- Полный горизонт 30 с сохраняется для каждого кандидата. Сначала выполняется равномерный круговой обзор шагом 5°; три лучших углово-разнесённых кандидата уточняются шагом 0,25° в окне ±3°. Предыдущий курс также локально уточняется, если его окно не покрыто выбранными лидерами. Это сохраняет поиск резких разворотов при существенно меньшем числе дорогих симуляций. Расстояние считается до непрерывного отрезка траектории за весь шаг; near-miss бонус помогает локальному уточнению, но не засчитывает сбор.
- Для одного ковра shortlist ограничен 48 ближайшими и 16 наиболее ценными дополнительными bounty (всего не более 64); сохранённая цель добавляется отдельно, если её нет в shortlist. Сбор проверяется по сегменту каждого серверного шага.
- Все курсы одного решения прогнозируются одним `horizon` и физическим шагом 0,2 с. Отдельная метрика маршрута — `routeScore`, сумма исходных points только монет, захваченных при касании суммы радиусов на сегменте тика (без временного discount и near-miss бонуса). Прибыльность — `scoreRate = routeScore / timeToLastBounty`, где `timeToLastBounty` — максимальное фактическое время среди всех собранных на маршруте bounty от текущего снимка, включая задержку применения команды. Оно агрегируется максимумом event-time, а не порядком обхода bounty/spatial grid. Окно у каждого пути собственное: пустое время после последней собранной монеты не учитывается. Если ни одна bounty не собрана, rate равен нулю.
- Угол из прошлого `PlanMemo` каждый тик перепрогнозируется на том же максимальном horizon и становится incumbent; его score-rate нормируется по времени до последней монеты на нём. Пока incumbent безопасен, его вектор удерживается, включая случай нулевого score-rate. Переключение разрешается только если безопасная альтернатива повышает rate не менее чем на `max(50% incumbentRate, 5 score/s)`. Поэтому небольшой шум оценок или случайный единичный перехват не дёргает курс; небезопасный incumbent сразу уступает безопасной альтернативе.
- Альтернативная стратегия `agile-top1` не использует `PlanMemo`, ETA commitment, detour и порог переключения. Каждый тик заново оценивает 360 фиксированных направлений с шагом 1° и горизонтом 15 с при физическом шаге 0,2 с, затем выбирает безопасный маршрут с максимальным `routeScore / timeToLastBounty` — как score-rate rank визуализатора. Безопасность выше score; безопасный маршрут без монет остаётся выше смертельного. В отличие от основной стратегии, скан использует все bounty snapshot, но проверяет их spatial grid broadphase по участкам сегментов. До применения команды учитывается lead 0,3 с, совпадающий с прогнозным веером. В планировщик отправляется вектор ускорения длиной `maxAccel` в направлении выбранной траектории; на следующем тике маршрут и вектор рассчитываются заново из нового состояния. Горизонт ограничен сверху 15 секундами.
- Новая стратегия `top1-v2` использует score-rate ranking и 15-секундный горизонт `agile-top1`, но сохраняет первую собираемую bounty и угол курса до сбора или потери безопасного прогресса. После сбора следующая монета планируется заново из свежего состояния. Полный выбор использует coarse scan 5° и уточняет до трёх лучших разнесённых областей шагом 0,25° в окнах ±3°; при удержании цели проверяется один incumbent-маршрут. Она использует все bounty snapshot и тот же сегментный spatial grid broadphase.
- Movement policy независима от выбора bounty: `none` не меняет aim-решение; `survival` проверяет прогноз на попадание в fatal cell сетки 350 world units. Фатальная ячейка — ядро, сильное некомпенсируемое притяжение в зоне захвата, сильное выталкивание у границы или ограниченная цепочка некомпенсируемой силы в такую область. Компенсируемое поле хранится как оценка риска <1 и не включает аварийный scan. Если aim-путь достигает fatal cell в горизонте 30 с, выполняется 5° full-circle scan на 30 с. Среди безопасных курсов сначала предпочитается сбор bounty и высокий score-rate; пустой курс используется, только если безопасного собирающего курса нет. Если ни одна из 72 проверяемых траекторий не переживает safety horizon, это «выход не найден в scan», а не доказательство смерти при любой мыслимой политике.
- При `DATS_DOOM_POLICY=collect` fatal candidates ранжируются по фактическому routeScore, затем score-rate и более поздней смерти; `fastest` сохраняет comparator максимальной скорости и быстрейшей смерти. Цель aim продолжает пересчитываться параллельно и снова управляет курсом, как только safety override перестаёт требоваться.
- Безопасность по-прежнему лексикографически выше прибыльности: incumbent, прогнозирующий смерть, не удерживается против безопасной альтернативы. Команда сохраняет длину `maxAccel`.
- `targetUtility = totalPotentialScore + 5 * exp(-timeToReachScore / 15) - courseChangeCost`. Штраф смены направления непрерывен, растёт до `max(12 points, 20% totalPotentialScore)` на отклонении 30° и не обрывается на малом угле. Разница средней скорости до 0,015 от `maxSpeed` считается шумом сравнения, а не причиной повернуть.
- При близкой безопасной цели сначала удерживается действующий перехват, затем учитываются значимые отличия скорости, utility и преемственность курса. Большой угол всё ещё выбирается для поворота/разворота, если он явно обеспечивает сбор, безопасность или существенный выигрыш.
- Каждый живой ковер получает ровно одну цель на каждом цикле. `CollectBounties` выбирается только для безопасной траектории, фактически пересекающей bounty; безопасный путь без монет означает `AvoidDeath`; если все просмотренные направления смертельны — `FastestDeath`.
- Для `AvoidDeath` безопасность важнее любых points. В `FastestDeath` минимизируется время гибели, а монеты на пути добавляют выгоду, не отменяя эту цель.
- Команда имеет направление выбранного курса и ненулевую длину: штатно `maxAccel`; при невалидном нулевом лимите — минимальный fallback `1e-6`.
- Каждая команда живого ковра всегда имеет модуль `maxAccel`, вне зависимости от цели. В сравнении кандидатных траекторий среди путей с одинаковым исходом выше приоритет у большей средней скорости и конечной скорости; при прочих равных смерть ускоряется, а не откладывается.
- Сервер не блокирует команду в зоне аномалии: `A_cmd` полной длины складывается с `W_anomaly`. Телеметрия различает отправленную команду и фактически применённый self-acceleration, чтобы обнаруживать расхождение.
- Подтверждаемый predicted capture использует пересечение сегмента серверного тика с суммарным радиусом ковра и монеты. Near-miss aiming bonus рассчитывается по минимальному расстоянию сегмента за пределами суммарного радиуса и не считается сбором; такой промах не активирует жёсткую фиксацию цели.

### Сканирование направлений

- Полный круг 360° сначала сканируется равномерно с шагом 5° (72 уникальных кандидата); резкий разворот назад входит в обзор наравне с любым другим курсом. Три лучших кандидата с неперекрывающимися областями уточняются полным горизонтом в окне ±3° с шагом 0,25°.
- Направление прошлого плана всегда добавляется к грубому набору и перепрогнозируется. Когда безопасная сохранённая цель остаётся фактически собираемой, этот точный прогноз становится выбранным курсом без сканирования остальных направлений. Иначе локальное окно прошлого курса уточняется, если оно не покрыто окнами лидеров. И near-miss, и сбор используют минимальное расстояние сегмента к bounty; сбор отличается тем, что дистанция должна быть не больше суммы радиусов.
- Поскольку основной проход уже покрывает все 360°, повторный аварийный scan не выполняется. При отсутствии безопасных направлений выбирается наиболее успешная смертельная траектория: максимальная скорость, затем кратчайшая гибель и награды на пути.
- Успешность сравнивается так: безопасность; подтверждённое удержание цели; `selectionUtility` (основанная на `totalPotentialScore`, `timeToReachScore` и цене смены курса); затем скорость, score-rate и преемственность направления. Это восстанавливает прежний вес качества маршрута и удержания цели; score-rate остаётся гистерезисом между тиками, а не главным краткосрочным переключателем. Безопасность по-прежнему лексикографически выше. Для смертельных траекторий приоритет остаётся у максимальной скорости, затем у скорейшей гибели. Команда во всех случаях имеет полную длину maxAccel.
- При активной закреплённой цели сначала сравнивается безопасное попадание в неё; среди попадающих кандидатов учитываются суммарный score и время его достижения. Боковые направления продолжают проверяться секторным обзором и локальным уточнением, но без существенного выигрыша не отбирают ковер у текущей монеты.

### Сетевой цикл

Первый запрос пустой. Каждый следующий POST содержит ускорения всех живых транспортов. RTT записывается монотонными часами; команды отклоняются и повторяются только после `429` и паузы не короче тика. Нестатус `alive` исключает транспорт из command batch. Если рядом существует неистёкшая аренда `manual_control_<token-hash>.json`, player_2 очищает отложенный пакет и приостанавливает API-цикл, чтобы не конкурировать с визуализатором на том же токене; после снятия/истечения аренды бот возобновляется с нового снимка. Для нестандартного размещения путь можно одинаково задать переменной `DATS_MANUAL_CONTROL_FILE` обоим процессам.

### Live-консоль

- В интерактивном терминале экран обновляется на месте, по одному компактному блоку из трёх строк на ковер: состояние/позиция/скорость; векторы команды, применённого ускорения и аномалии; цель/очки/score-rate/риск.
- Заголовок показывает HTTP RTT, чистое время планирования (`plan ms`), число расчётов траекторий и оценку интеграционных шагов. Для оценки real-time запаса показываются доля планирования от бюджета тика 200 мс, полное время цикла, среднее сглаженное время планирования, максимум и число пропусков дедлайна.
- `A_next` (команда, рассчитанная для следующего запроса) и `A_now` (фактически применённое ускорение из полученного снимка) отображаются раздельно, чтобы не смешивать соседние тики.

## 5. API-контракты и DTO

| Метод | Путь | Тело |
|---|---|---|
| POST | `/play/magcarp/player/move` | `{"transports":[]}` для снимка; либо `{ "transports": [{"id":"…", "acceleration":{"x":number,"y":number}}] }` |

Ответ использует внешний контракт Desert API. Заголовки: `X-Auth-Token`, `Content-Type: application/json`. Player_2 потребляет этот контракт, но не меняет и не владеет серверным API.

## 6. Обработка ошибок

- `429`: ждать минимум один тик, добавить ограниченный jitter и повторить тот же пакет.
- HTTP/JSON/TLS ошибка: оставить последний план и повторить опрос после exponential backoff; TLS ошибки должны явно указывать origin и причину валидации/handshake.
- `errors[]` содержит ошибки команд; соответствующие IDs показывать в статусе телеметрии и отправлять безопасный пакет на следующем тике.
- Погибший/отсутствующий транспорт не получает управляющую команду.

## 7. Консольная телеметрия

- В интерактивном терминале показывается обновляемая на месте панель, а не строка на каждый тик. По каждому транспорту выводятся ID и состояние, позиция, вектор скорости и его модуль, `anomalyAcceleration`, `selfAcceleration`, отправляемый вектор команды, цель/координаты/ценность, дистанция, число bounty, `routeScore`, `timeToLastBounty`, `scoreRate`, `totalPotentialScore`, `timeToReachScore`, прогноз смерти и причина (если есть).
- Верхняя строка панели содержит длительность/номер опроса, RTT, число живых ковров, оставшиеся bounty, параметры мира и статус соединения.
- Ошибки и ожидание `429` отражаются в статусе панели, без спама повторяющимися сообщениями. Фатальная ошибка при завершении выводится отдельно.
- При перенаправленном stdout интерактивная панель отключена; краткая сводка печатается не чаще одного раза в 5 секунд. Отображение не меняет стратегию, команды или частоту запросов.

## 9. Тестирование

- `TC-PLAYER-PHYSICS-01`: без аномалий один Rust шаг совпадает с Euler сервером и ограничениями скорости.
- `TC-PLAYER-PLANNER-01`: кандидат, который собирает bounty и не достигает lethal-radius, выбирается раньше смертельного.
- `TC-PLAYER-TARGET-01`: цель удерживается, пока текущий безопасный план её собирает; малое преимущество не вызывает смену курса.
- `TC-PLAYER-SCORE-01`: для кандидатов сравниваются суммарный ожидаемый score, время первой награды и цена отклонения курса.
- `TC-PLAYER-SPEED-01`: при равном исходе более быстрая траектория выигрывает у курса с большей наградой; ускорение команды равно `maxAccel`.
- `TC-PLAYER-AIM-01`: coarse scan содержит 72 равномерных направления на полном круге с шагом 5°, включая точно противоположное направление; локальная доводка содержит 25 направлений на окно ±3° с шагом 0,25°; near-miss bonus не засчитывает bounty как собранную.
- `TC-PLAYER-PERF-01`: при валидной безопасной закреплённой цели на тик выполняется один прогноз сохранённого направления и не запускается круговой scan; без commitment оцениваются полный coarse-круг и не более трёх уникальных окон уточнения (плюс непокрытое окно incumbent).
- `TC-PLAYER-PROGRESS-01`: ETA закреплённой bounty должно прогрессировать между тиками; два последовательных тика стагнации освобождают цель и дают альтернативам возможность сменить курс.
- `TC-PLAYER-DETOUR-01`: ближний курс принимается как временный только если фактически собирает другую bounty за ≤5 с, даёт firstBountyRate выше базового на `max(50%, 5 points/s)` и переживает полный 30-секундный прогноз; после сбора выполняется безопасный возврат к сохранённой исходной bounty.
- `TC-PLAYER-SAFETY-01`: ни большой общий score, ни высокий краткосрочный score-rate не могут предпочесть смертельную траекторию безопасной.
- `TC-PLAYER-BOUNTY-01`: bounty засчитывается при минимальной дистанции от центра монеты до сегмента движения за тик не больше суммы радиусов; касание на границе засчитывается, внешний near-miss — нет.
- `TC-PLAYER-SCORE-RATE-01`: при сборе нескольких bounty на одном шаге `timeToLastBounty` равен времени наиболее позднего пересечения и не зависит от порядка элементов spatial grid.
- `TC-PLAYER-PROFIT-01`: score-rate равен actual routeScore/timeToLastBounty для каждого маршрута; near-miss не считается earned score; положительный incumbent удерживается при малом приросте альтернативы, нулевой уступает любому безопасному положительному курсу, а небезопасный никогда не удерживается.
- `TC-PLAYER-API-01`: кодирует токен и transport batch в точный Desert-контракт, успешно разбирает snapshot и 429.
