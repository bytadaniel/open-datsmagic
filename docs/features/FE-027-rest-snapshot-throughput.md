# FE-027: Пропускная способность REST-снимка арены

## 1. Контекст и цель

Игровой REST endpoint возвращает полный Desert snapshot на каждый запрос. Большие миры дают ответы порядка сотен килобайт, поэтому сетевой объём и сериализация могут стать узким местом при нескольких командах. Требование — обслуживать не менее 10 активных команд при неизменном игровом контракте и периоде тика 200 мс.

## 2. Архитектурное решение

- Сохраняется единственный игровой маршрут `POST /play/magcarp/player/move`, существующая авторизация и JSON schema.
- Arena согласует gzip только если клиент явно передал `Accept-Encoding: gzip`; иначе возвращает прежний несжатый JSON.
- Auth middleware ограничивает каждый известный игровой токен пятью запросами в скользящем окне 1 с и отклоняет лишние запросы с `429` до API handler. Observer credential не делит лимит между всеми анонимными наблюдателями.
- Лимит `5 запросов/с` ограничивает HTTP-запросы независимо от содержимого; прежний лимит «один непустой пакет команд за тик симуляции» сохраняется отдельно.
- Ответ при gzip содержит стандартный `Content-Encoding: gzip` и корректную длину сжатого тела. HTTP-клиент обязан декодировать представление перед JSON parsing.
- Hub proxy запрашивает gzip у arena и прозрачно пересылает сжатое тело и `Content-Encoding`, чтобы сократить внешний сетевой трафик.
- Встроенный HTTP transport player_2 включает gzip negotiation и декодирование, не изменяя payload/DTO.
- Измерять отдельно время тика, время обработки HTTP, размер до/после сжатия и latency при 1/10 одновременных клиентах. Нагрузка создаётся уникальными командами/токенами; несколько запросов одного токена и observer-only нагрузка не считаются эквивалентом.

## 3. Алгоритмы и ограничения

Сжатие выполняется после построения Desert DTO и только по явному согласованию клиента. Оно не меняет правила игры, частоту тиков, лимит запросов и команды. Не использовать очередь устаревших ответов: при тестировании учитывать один запрос на команду за тик.

## 4. API-контракт

Новых маршрутов и полей нет. Запрос может добавить заголовок:

```http
Accept-Encoding: gzip
```

При поддержке сжатия ответ включает:

```http
Content-Type: application/json
Content-Encoding: gzip
```

Тело после стандартной HTTP-декомпрессии полностью соответствует существующему Desert JSON.

## 5. Обработка ошибок

| Случай | Результат |
|---|---|
| Превышен лимит игрового токена | `429` до чтения/сериализации snapshot |
| Клиент не запросил gzip | Несжатый JSON, прежнее поведение |
| Клиент запросил gzip | Сжатый JSON и `Content-Encoding: gzip` |
| Ошибка формирования/сжатия ответа | Ошибка сервера; частичное или некорректное JSON-тело не отправляется |

## 7. Тестирование

- Без `Accept-Encoding` ответ остаётся обычным JSON без `Content-Encoding`.
- Шесть запросов одного токена в скользящую секунду дают пять допущенных и один `429`; другой токен имеет независимую квоту.
- С `Accept-Encoding: gzip` ответ распаковывается и даёт прежний Desert DTO.
- Hub сохраняет `Content-Encoding` и байты сжатого тела без двойного сжатия.
- Ограниченный нагрузочный тест использует 10 разных зарегистрированных команд, частоту не выше одного запроса на тик; фиксируются p50/p95, ошибки, байты, CPU и tick overrun.
