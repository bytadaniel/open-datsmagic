# FE-020: Каталог профилей мира в JSON

## 1. Контекст и цель

Хранить коллекцию разнообразных, готовых к запуску миров отдельно от Rust-кода и БД. Размер каталога задаётся содержимым JSON (один или более профилей), включая режимы без респавна; арены и объём сущностей остаются ограниченными. Каждый профиль должен иметь ясную игровую особенность, выраженную конкретными настройками и описанием, а не отличаться только ID или близкими числами.

## 2. Архитектура

`assets/worlds.json` содержит записи `{id, name, description, config}`. В каждой записи `config` — явные overrides параметров `ServerConfig`; сервер десериализует, дополняет defaults и валидирует их. Никакого вычисления профиля по сид-значению или копирования профиля в БД нет.

Hub получает каталог через read-only CLI `--world-catalog-json` (CLI читает тот же `assets/worlds.json`, что и обычный сервер), случайно выбирает `world_id`, передаёт его в `DATS_WORLD_ID` и сохраняет в строке запуска только ID/номер/название. Повтор одного профиля гарантирует те же настройки, но не ту же случайную расстановку сущностей. Спавнеры получают отдельную runtime-энтропию процесса; тесты могут задавать фиксированную энтропию.

`current_world.json` — пересоздаваемый runtime-снимок выбранного ID/номера/названия/описания и применённой конфигурации. Он не является каталогом. Tick rate фиксирован на 200 мс и профилями не переопределяется. `HOST`/`PORT` остаются сетевыми override.

## 3. Каталог и ресурсные пределы

- Каталог: [`worlds.json`](../../assets/worlds.json); число записей не зашивается в код.
- ID уникален и стабилен; имя и контекстное описание лежат рядом с настройками.
- Ширина и высота каждой арены находятся в диапазоне 8 000–20 000.
- Запас монет варьируется от примерно 500 в бедных мирах до 12 000 в богатых; типичные миры целятся в 4 000–7 000.
- Размер флота задаётся `carpet_count` от 1 до 10; по умолчанию — 5.
- Профили включают спокойные, аномально сильные, штормовые, быстрые/медленные и скользкие/вязкие миры.
- Описание каждого профиля называет конкретное отличие и его игровой эффект; не допускается повтор одного описания для формально разных профилей.
- Особые сценарии с одним ковром без респавна и с десятью коврами без респавна являются стабильными профилями; каталоговые правки не должны менять их конфигурации.
- Каталог может включать мир с малым ядром, почти равным области воздействия: радиусы задаются близкими диапазонами, но не раздуваются до размеров карты.

## 4. Валидация и тесты

- Unit: JSON содержит один или более уникальных ID; обязательные строки непустые.
- Unit: каждый профиль десериализуется и проходит серверную валидацию; ограничения арены, флота и монет соблюдены.
- Unit: выбор каталожного ID возвращает именно его профиль; неизвестный ID отклоняется.
- Unit: миры заметно различаются по нескольким параметрам, включая физику, аномалии и запас монет.
- Review: у каждого профиля читается отдельная фишка из описания и конфигурации; большие каталоги не набираются косметическими дублями.
- Unit: мир с ядрами, близкими к области воздействия, проходит ту же серверную валидацию радиусов, что и остальные профили.
- Unit: `near-core-field` сохраняет отношение минимального радиуса ядра к максимальному радиусу зоны не ниже 0,8 и ограничивает радиус ядра 400 игровыми единицами.
- Integration: Hub и сервер читают один JSON-каталог; конфигурация не хранится в SQLite.
- UI: `/worlds` и окно визуализатора показывают ID, название, описание и конфигурацию, не показывая seed.
