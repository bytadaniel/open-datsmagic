# DR-014: Веб-наблюдение и ручное управление ареной

## 1. Бизнес-контекст

**Проблема / Возможность:** Hub предоставляет страницы команд и результатов, но не даёт наблюдать за живой ареной или вручную управлять собственным ковром из браузера.

**Цель:** дать анонимному зрителю лёгкий интерактивный экран арены и зарегистрированному игроку — возможность управлять одним своим ковром без построения прогнозов.

**Пользователи / Роли:** анонимный наблюдатель смотрит публичный снимок арены; владелец зарегистрированного токена видит свой флот и отдельно включает ручное управление одним своим живым ковром.

**Ключевые метрики:** частота успешных снимков, частота кадров отрисовки, доля времени без сетевых ошибок.

## 2. Сценарии использования

### 2.1 Основной сценарий

| № | Участник | Действие | Результат |
|---|---|---|---|
| 1 | Игрок | Открывает визуализатор и вводит свой зарегистрированный токен | Hub получает снимок через игровой API; токен не помещается в URL |
| 2 | Игрок | Выбирает ковер и включает центрирование | Камера плавно следует за сущностью |
| 3 | Игрок | Включает ручное управление для собственного ковра | Hub передаёт вектор ускорения и обновляет совместимую аренду управления ботом |
| 4 | Игрок | Выключает ручной режим или теряет соединение | Аренда прекращается немедленно либо истекает по TTL; бот может возобновить управление |
| 5 | Наблюдатель | Открывает визуализатор без токена | Read-only снимок всей арены; дополнительный игрок/флот не создаётся |
| 6 | Посетитель | Включает полноэкранный режим | Карта занимает экран и сохраняет доступ к основным контролам |

### 2.2 Альтернативные сценарии

- Режим наблюдателя перемещает камеру стрелками/перетаскиванием и не отправляет ускорение.
- На телефоне одно касание перемещает камеру, щипок меняет масштаб, а отдельный виртуальный стик управляет выбранным ковром.
- При смене арены клиент показывает состояние подключения и продолжает получать снимки того же токена на новой арене.

### 2.3 Исключительные ситуации

| Условие | Реакция системы |
|---|---|
| Токен отсутствует в реестре Hub | Показать ошибку авторизации, не раскрывая его значение |
| Игровой сервер недоступен / вернул ошибку | Показать reconnect-состояние, сохранить камеру и выбор, не теряя UI |
| Выбран погибший ковёр | Наблюдение разрешено; ручной ввод отключён до его оживления |
| Выбран вражеский ковер | Наблюдение разрешено; ручное управление запрещено |

## 3. Функциональные требования

| ID | Требование | Приоритет | Примечание |
|---|---|---|---|
| FR-01 | Визуализатор показывает арену, аномалии, монеты, свои и вражеские ковры | Must have | Без траекторий и карт риска |
| FR-02 | Пользователь выбирает любой видимый ковер и отдельно включает слежение камерой | Must have | Выбор не включает ручное управление |
| FR-03 | Для выбранного ковра отображаются векторы скорости, собственного ускорения и силы аномалий | Must have | Подписи/легенда должны различать векторы |
| FR-04 | Камера поддерживает зум и панорамирование с клавиатуры, мыши и сенсорных жестов | Must have | Координаты карты не инвертируются для ввода |
| FR-05 | Токенизированный игрок может вручную управлять одним своим живым ковром | Must have | Другие ковры не входят в ручной режим |
| FR-06 | Клиент интерполирует сетевые снимки только для плавности отображения | Should have | Симуляция остаётся на сервере |
| FR-07 | Ручной режим доступен с мыши и с мобильного виртуального стика | Must have | Максимум ускорения соответствует `maxAccel` |
| FR-08 | Анонимный наблюдатель видит всю арену без регистрации и создания ковров | Must have | Серверный observer credential никогда не возвращается клиенту |
| FR-09 | Монеты сохраняют пропорциональный мировому радиусу размер при любом zoom | Must have | Рисовать по исходным координатам, без масштабирования растрового слоя |
| FR-10 | Визуализатор включает и выключает fullscreen на desktop/mobile | Should have | Работает также через fullscreen API браузера |

## 4. Нефункциональные требования

| ID | Требование | Значение / Описание |
|---|---|---|
| NFR-01 | Частота отрисовки | Целевой 60 FPS на настольном браузере и плавность на смартфоне; не запускать тяжёлые прогнозы |
| NFR-02 | Частота сетевых снимков | Не чаще одного запроса на тик мира (200 мс) |
| NFR-03 | Безопасность | Токен передаётся только в теле POST и заголовке к игровому API, не в URL/логах/HTML |
| NFR-04 | Отказоустойчивость управления | Совместимая аренда имеет короткий TTL и обновляется только пока включено ручное управление |

## 5. Бизнес-правила

1. Игровой API остаётся единственным источником состояния; Hub проксирует его единственный игровой POST, не создавая второго API чтения арены.
2. Пустой пакет команд используется для получения снимка и не меняет ускорение ковров.
3. Любой ковер можно выбрать для наблюдения, но команду разрешено послать только собственному ID из `transports` пользователя.
4. Вектор мыши/стика ограничивается длиной `maxAccel`; направление по экранной оси Y преобразуется в систему координат карты.
5. В режиме ручного управления Hub обновляет lease `manual_control_<token-hash>.json`, используемый player_2 для уступки команд; lease ограничен по времени и не хранит сам токен.
6. Отрисовка и интерполяция не меняют состояние симуляции и не запускают прогнозную физику.
7. Observer credential доступен только arena-процессу через переменную окружения Hub; observer-команда с любыми transports отклоняется, player state не создаётся.

## 6. Модель данных

| Сущность | Описание | Ключевые атрибуты |
|---|---|---|
| Snapshot | Полный ответ игрового API | `mapSize`, `bounties`, `anomalies`, `transports`, `enemies`, `maxSpeed`, `maxAccel` |
| CameraState | Клиентское состояние камеры | `center`, `zoom`, `followId` |
| ManualLease | Короткая аренда управления между веб-клиентом и player_2 | `carpetId`, `leaseId`, `expiresAtUnixMs` |

## 7. API-контракты

| Метод | Путь | Назначение | Параметры |
|---|---|---|---|
| POST | `/api/visualizer/move` | С токеном Hub проксирует команду своей команды; без токена — только read-only observer запрос | `{token?, transports, manualCarpetId?, leaseId?}` |

Успешный ответ — неизменённый Desert snapshot. Игровой контракт `POST /play/magcarp/player/move` остаётся единственным игровым endpoint.

## 8. Критерии приёмки

- [ ] Видны аномалии, монеты, свои и вражеские ковры без траекторий и тяжёлых расчётов.
- [ ] Любой ковер выбирается кликом или из списка; отдельный переключатель центрирует камеру.
- [ ] Выбранный ковер показывает velocity, selfAcceleration и anomalyAcceleration.
- [ ] Зум, панорамирование и выбор работают мышью, клавиатурой и сенсорными жестами.
- [ ] Ручная команда принимается только для собственного живого ковра; вектор не превышает `maxAccel`.
- [ ] При ручном управлении player_2 уступает выбранный ID; после выключения/потери клиента lease освобождается или истекает.
- [ ] Без токена видна вся арена, новый игрок/ковер не появляется, управляющие команды невозможны.
- [ ] Размер монеты соответствует мировому радиусу при зуме без растрового размытия.
- [ ] Fullscreen включается/выключается на поддерживаемых браузерах; карта и контролы адаптируются для телефона.
- [ ] Токен не появляется в URL, исходной странице или логах.

## 9. Вопросы и допущения

**Допущения:**
1. Чтение снимков через игровой POST с пустым `transports` является допустимым способом наблюдения, так как отдельного GET API нет.
2. Все сервисы на начальном этапе используют общий репозиторный filesystem для файла lease; при раздельных контейнерах путь должен стать общей volume или координацией через Hub.

## 10. Зависимости

- **Внутренние модули:** `apps/arena-hub`, игровой Desert API, `lib/bot-variants/player_2` lease.
- **Инфраструктура:** активный arena endpoint и общий путь краткосрочной аренды управления.
