# DR-009: Контракт мира внешнего симулятора и телеметрия транспорта

## 1. Бизнес-контекст

Старый клиент в `./datsmagic` является единственным источником истины для внешнего API мира. Его TypeScript-типы, API-вызовы и сохраненный ответ `map.json` фиксируют точные маршрут, метод, заголовок и поля, необходимые самостоятельным клиентам. Это не реализация стратегии и не код, который должен быть перенесен на сервер.

**Цель:** документировать расхождения между этим контрактом и текущим DatsMagic, чтобы последующие изменения были намеренной миграцией, а не догадкой.

**Роли:** игровой клиент читает мир и отправляет команды; сервер валидирует их и возвращает новый снимок; визуализатор отображает только телеметрию.

## 2. Сценарии использования

| № | Участник | Действие | Результат |
|---|---|---|---|
| 1 | Клиент | `POST /play/magcarp/player/move` с `X-Auth-Token` и `transports` | Получает полный снимок Desert. |
| 2 | Клиент | Передает для ковра `id`, `acceleration`, при необходимости shield/attack | Сервер применяет допустимую команду. |
| 3 | Клиент | Читает `transports`, `anomalies`, `bounties`, `enemies` | Самостоятельно выбирает стратегию. |

**Исключения:** `429` означает, что клиент должен отложить повтор команды; поле `errors[]` содержит ошибки отдельных транспортов и не отменяет снимок мира.

## 3. Функциональные требования

| ID | Требование | Приоритет | Примечание |
|---|---|---|---|
| FR-01 | Публичный API должен в точности реализовывать маршрут и JSON-контракт референсного клиента. | Must have | `POST /play/magcarp/player/move`, точный `Desert` без альтернативных имен полей. |
| FR-02 | Для каждого транспорта должны передаваться три телеметрических вектора. | Must have | См. правила ниже. |
| FR-03 | Аномалия должна различать радиус ядра и эффективный радиус, знак силы и скорость. | Must have | `radius`, `effectiveRadius`, `strength`, `velocity`. |
| FR-04 | Контракт должен возвращать bounties, противников, статусы и ошибки частичных команд. | Should have | Требует отдельных фич реализации. |

## 4. Нефункциональные требования

| ID | Требование | Значение / Описание |
|---|---|---|
| NFR-01 | Единственный маршрут | Сервер и визуализатор используют только `POST /play/magcarp/player/move`; маршруты `/api/*` отсутствуют. |
| NFR-02 | Изоляция стратегии | Сервер не переносит pathfinding или эвристики из `./datsmagic`. |
| NFR-03 | Валидность чисел | Векторы и лимиты не допускают `NaN` и бесконечность. |

## 5. Бизнес-правила

1. **Три вектора транспорта:** `velocity` — текущая скорость, `selfAcceleration` — последнее эффективное собственное ускорение после ограничения `maxAccel`, `anomalyAcceleration` — результирующее ускорение/сила от аномалий. Положение (`x`, `y`) — координаты, а не один из этих трех векторов.
2. **Знак силы аномалии:** положительный `strength` означает притяжение, отрицательный — отталкивание; `effectiveRadius` задает область силы, `radius` — опасное ядро.
3. **Команда транспорта:** клиент направляет только желаемое `acceleration`; shield и attack — независимые опциональные команды.
4. **Возрождение:** `status`, `health`, `deathCount` и `reviveTimeoutSec` описывают жизненный цикл транспорта; это отличается от текущего мгновенного респавна демонстрационного сервера.
5. **Список `enemies`:** поскольку каждый токен владеет флотом ковров, сервер сериализует каждый ковер всех остальных токенов отдельной записью в плоском массиве `enemies`. В legacy DTO нет `id`, поэтому порядок записей должен быть стабилен по ID игрока и ковра внутри сервера.

## 6. Модель данных

| Сущность | Ключевые атрибуты |
|---|---|
| `Desert` | `mapSize`, `points`, лимиты, `transports`, `anomalies`, `bounties`, `enemies`, `errors` |
| `Transport` | `id`, `x/y`, `velocity`, `selfAcceleration`, `anomalyAcceleration`, `health`, cooldowns, `status`, lifetime `deathCount` (monotonic for stable carpet id, including same-tick respawn) |
| `Anomaly` | `id`, `x/y`, `radius`, `effectiveRadius`, `strength`, `velocity` |
| `Bounty` | `x/y`, `radius`, `points` |

## 7. API-контракты

| Метод | Путь | Назначение | Тело |
|---|---|---|---|
| POST | `/play/magcarp/player/move` | Получить состояние и применить пакет команд | `{ "transports": [{"id", "acceleration?", "activateShield?", "attack?"}] }` |

`datsmagic/src/api/get-map.ts` не задает отдельный маршрут карты: он вызывает этот же `POST` с `{ "transports": [] }`. Это канонический запрос снимка `Desert`.

Этот маршрут и тип `Desert` являются единственным контрактом всех клиентов, включая визуализатор. Полный образец ответа сохранен в [`datsmagic/map.json`](../../datsmagic/map.json); источники типов и вызова — `datsmagic/src/api/get-map-types.ts` и `move.ts`.

## 8. Критерии приемки

- [x] AC-01: API возвращает в точности ключи типа `Desert` из `get-map-types.ts`; монеты передаются как `bounties`.
- [x] AC-02: Документация явно отличает `selfAcceleration` и `anomalyAcceleration` от координат.
- [ ] AC-03: Для каждого отсутствующего поля есть отдельная техническая фича миграции.
- [ ] AC-04: Поведенческий код клиента в `./datsmagic` не изменен.

## 9. Вопросы и допущения

- Формула `strength` и точный порядок интегрирования внешнего сервера не следуют однозначно из клиента; их нельзя переносить без эталонной серверной спецификации.
- Внешний API использует `POST` и для пустого опроса с `transports: []`; текущий API использует `GET` для чтения.

## 10. Зависимости

- Эталон: `./datsmagic/map.json` и `./datsmagic/src/api/`.
- Целевые модули: `server::api`, `server::physics`, `server::spatial`, `visualizer`.
