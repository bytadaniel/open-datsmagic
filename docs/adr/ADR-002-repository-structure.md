# ADR-002: Структура репозитория и организация кодовой базы

## 1. Контекст и проблема

Проект **DatsMagic** представляет собой сложную распределенную систему симулятора игрового мира, состоящую из:

1. Высокопроизводительного игрового сервера симуляции на языке **Rust**.
2. Автономного Rust-клиента визуализации в `visualizer_2/` (Python-клиент остается legacy fallback).
3. Комплексной системы документации в парадигме **Spec-Driven Design (SDD)**, являющейся единственным источником правды (SSOT).

### Ключевые требования:

- **Разделение ответственности и изоляция окружений**: сервер и Rust-визуализатор — отдельные приложения с независимыми зависимостями; legacy Python-клиент изолирован отдельно.
- **Единый репозиторий (Monorepo)**: Все компоненты системы должны находиться в одном репозитории для обеспечения согласованности версий спецификаций, серверных DTO и сетевых протоколов.
- **Спецификации как фундамент (Docs-First)**: Документация должна занимать центральное место в репозитории с фиксированной иерархией.
- **Ориентация на AI-разработку**: Прозрачная и предсказуемая топология каталогов, строгое соответствие путей к исходному коду модулям, заявленным в Feature Specs (`FE-xxx`).

## 2. Архитектурное решение (Декларативные предписания)

Принято решение организовать проект по принципу **монорепозитория** со строгим разграничением ответственности между каталогами.

## 3. Детализация подсистем и стандарты размещения

### 3.1. Корневой уровень и Cargo Workspace

- В корне репозитория создается манифест `Cargo.toml`, объявляющий **Cargo Workspace**.
- Корневой манифест включает директорию `server` в качестве члена воркспейса (`members = ["server"]`).
- Это позволяет запускать `cargo build`, `cargo test`, `cargo clippy` и `cargo fmt` как из корня проекта, так и внутри каталога `server/`.
- Выходные исполняемые файлы компилируются в единую корневую директорию `target/` (в `.gitignore`).

### 3.2. Документация (`docs/`)

- Каталог `docs/` не содержит исполняемого кода и управляется по правилам `AGENTS.md`.
- Все документы именуются в соответствии с префиксами:
  - `docs/adr/ADR-xxx-<name>.md`
  - `docs/domain/DR-xxx-<name>.md`
  - `docs/features/FE-xxx-<name>.md`
- Путь к модулю в метаданных фичи (например `module: "server::engine"`) должен зеркально отражать структуру подкаталогов `server/src/engine/`.

### 3.3. Сервер симулятора (`server/`)

- Каждый функциональный модуль оформляется в виде отдельного подкаталога в `src/` с заглавным файлом `mod.rs` (фасад модуля) либо отдельного файла, если модуль атомарен.
- Публичный интерфейс (`pub trait`, `pub struct`) экспортируется через фасад модуля.
- Внутренние структуры и детали реализации инкапсулируются (`pub(crate)` или `pub(super)`).
- Интеграционные тесты выносятся в `server/tests/`, изолированные модульные тесты размещаются в файлах модулей внутри подмодулей `#[cfg(test)] mod tests`.

### 3.4. Legacy-визуализатор (`visualizer/`)

- Изолирован от Rust-кода и не использует общих файлов сборки.
- Использует стандартную структуру пакета Python с изоляцией зависимостей через `requirements.txt` / виртуальное окружение (`venv`).
- Сохранен для сравнения и fallback; основным UI-клиентом является отдельный Rust-crate `visualizer_2/`.

### 3.5. Основной нативный визуализатор (`visualizer_2/`)

- Самостоятельный Cargo crate с локальной документацией в `visualizer_2/docs/`.
- Использует `eframe/egui` с renderer `glow`, REST/API-модели не связываются линковкой с серверным crate.
- Поведение клиента специфицировано локальными ADR, DR и FE; игровой контракт берется из корневого `docs/`.

## 4. Обоснование структуры (Trade-offs)

| Аспект решения                             | Выбранный подход                                                           | Альтернатива                                                 | Обоснование                                                                                                                                                                                                                                                                                                                                                                          |
| :------------------------------------------------------ | :---------------------------------------------------------------------------------------- | :----------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Организация репозитория** | Монорепозиторий (Monorepo)                                                 | Полирепозиторий (Polyrepo)                                | Обеспечивает единую синхронизацию спецификаций SDD, серверного ядра и клиента визуализации в одном Git-дереве.                                                                                                                                                                                         |
| **Сборка Rust**                             | Cargo Workspace в корне                                                             | Изолированный Cargo проект только в`server/` | Корневой воркспейс позволяет запускать линтеры и тесты из корня репозитория единой командой`cargo test`. При необходимости расширения (например, отдельный крейт общих протоколов) воркспейс легко масштабируется. |
| **Модульность сервера**         | Доменная декомпозиция (`engine`, `physics`, `spatial`, `api`) | Плоская структура файлов (`src/*.rs`)            | Соответствует принципам SOLID и строго отражает спецификации`FE-001` .. `FE-004`.                                                                                                                                                                                                                                                          |
| **Изоляция визуализатора**   | Отдельный `visualizer_2/` Rust-crate                            | Встраивание UI в бинарник сервера                    | Графические зависимости не увеличивают серверный бинарник; интеграция идет по REST.                                                                                                                                                                                                                                      |

## 5. Последствия (Consequences)

### Положительные:

1. **Четкое соответствие спецификациям**: Каждый модуль в `server/src/` однозначно сопоставлен с конкретной `FE-xxx` спецификацией в `docs/features/`.
2. **Прозрачность для AI-агентов**: Агент безошибочно определяет, в какой каталог помещать новые файлы реализации и тесты.
3. **Изоляция процессов и сред**: сервер, Rust-визуализатор и legacy Python-клиент имеют независимые зависимости.
4. **Удобство непрерывной интеграции (CI)**: Возможность независимо собирать сервер и визуализатор.

### Отрицательные и риски:

1. Необходимость поддержания корневого `.gitignore`, покрывающего артефакты обеих экосистем (`target/`, `.pytest_cache/`, `__pycache__/`, `.venv/`).
2. При изменении серверных DTO в `FE-004` / `server/src/api/dto.rs` требуется явный аудит моделей в `visualizer_2/`.
